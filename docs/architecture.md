# `legado_rs` 架构约定

本文记录项目已确定的产品边界和数据流。实现可以演进，但不得越过这些边界；若某个功能与边界冲突，应重做方案并把原因、决定和验证记入 [`decisions.md`](decisions.md)。

## 产品范围

- `legado` 是只读的旧版功能及成熟界面参考，不继续开发，也不直接照搬已知缺陷、错误逻辑或未完成的界面/功能。
- `legado_rs` 是新产品和唯一开发目标，最终覆盖旧应用中有效、成熟的全部能力，并提供完整、可用的实现和相应 UI。遇到旧实现有缺陷或只有未接通的 UI 时，应按功能目的补成正确可用的行为。
- 统一推进 Android、桌面端（Windows、macOS、Linux）和 iOS；鸿蒙不纳入目标。
- 不迁移、不重写现有 Kotlin/KMP 书源引擎。Rust 当前负责调用和协调 KMP；将引擎迁到 Rust 属于未来可选优化。
- 继续支持现有引擎可以执行的书源规则及书源 JSON 格式。新项目不承诺读取旧版书架、进度、设置或备份数据。

## 核心职责边界

业务链路固定为：

```text
JS / WebView 接收交互
        │ 轻量命令 / 用户意图
        ▼
Rust 处理全部中间业务 ──可调用──> Kotlin/KMP 书源引擎
        │ 准备或修改最终资源，并发送轻量状态通知
        ▼
JS / WebView 读取资源、处理展示并响应后续展示交互
```

- **JS/WebView 的第一站职责**：接收点击、搜索词、删除、打开书籍、阅读进度等用户意图，并在需要业务处理时委托 Rust。书源编辑界面可以收集用户配置输入，保存、校验、导入等配置操作经 Rust 执行。
- **Rust 的中间职责**：统一承接业务命令，执行书源请求调度、任务、网络和资源准备，调用现有 KMP 引擎执行书源定义中的全部规则与脚本，整理最终数据，读写持久化文件，并在数据变化时通知前端。前端不能执行书源规则、解析书源定义来取得业务结果，也不能把未经引擎处理的书源定义当成展示资源消费。
- **Kotlin/KMP 的职责**：执行兼容现有书源格式的书源规则、脚本和解析器逻辑。当前阶段保留已有引擎实现，不以代码语言作为架构边界；在 Tauri 应用中，书源引擎的请求、HTTP、Cookie、代理及存储仍由 Rust 宿主路径协调。
- **JS/WebView 的最后一站职责**：直接消费已经准备好的 JSON/HTML/图片等资源并完成 UI 展示。资源可来自本地文件 URL、带认证处理的资源服务 URL 或直接远程 URL；消费端依据 `src` 读取，不因来源不同重新承担中间业务。
- **已有资源不需要逐次经过 Rust**：翻页、展示、在已加载目录中切换章节、读取已缓存章节，以及字号/行距/颜色等显示调整，均由 JS 基于已有资源完成。只有资源不足、需要执行规则、修改持久化数据或其它中间业务时才委托 Rust。
- IPC 用于用户意图、结果状态、取消/错误等轻量控制信息及资源入口；大段正文、媒体和图片不因展示而反复通过 IPC 搬运。

## 持久化与资源格式

- **不引入 SQLite**。书架、书目与目录索引、阅读进度、阅读/应用设置、书源及规则配置、任务状态、书签、历史记录等应用结构化数据，底层以 JSON 文件保存。JSON 既是持久化格式，也可作为前端通过资源地址直接读取的消费格式；Rust 负责读写，JS 不直接操作应用数据目录。
- **章节正文以 HTML 缓存**，不塞进 JSON。HTML 保存引擎已经处理过的章节内容以及默认阅读样式（例如初始字体大小和相关排版值）。书籍/目录 JSON 中章节 `src` 指向本地可访问地址或远程 URL。
- 图片、音频、视频及其它二进制内容作为独立资源，通过 URL/`src` 消费。若资源需要书源认证或协议代理，Rust 准备可消费的资源 URL，并正确处理资源请求；不能要求前端执行书源规则来取得资源。
- `src` 表示运行时可读的资源地址。书籍 JSON 持久化其业务索引和来源信息；本地文件地址可以持久化为稳定的应用资源地址/相对资源标识，运行时变化的代理端口不能成为长期数据契约。
- 阅读器读取章节 HTML 后，JS 应用用户当前设置覆盖 HTML 默认样式，显示层第二道用户自定义替换也在 JS 展示路径完成；这些修改仅影响当前展示，不改写已缓存章节 HTML。书源规则本身的内容清理/替换仍只由书源引擎处理，缓存的是引擎已处理的结果。
- JS 在打开书籍或推进到后续章节时，基于图书 JSON 和缓存 `src` 判断可用章节是否充足；不足时通知 Rust 获取并缓存适量章节、更新图书 JSON 和资源地址，再通知 UI。翻到已经可用的章节不需要请求 Rust。
- 阅读期间 JS 可以低频记录交互进度，并在离开书籍、应用进入后台等可捕获的生命周期时委托 Rust 更新进度 JSON。Rust 对文件写入负责。验收需覆盖正常离开/后台恢复与重启恢复；不能把“系统强杀时一定收到退出回调”作为保证。
- 删除书籍、更新书架以及其它文件变化同样由 JS 发出意图、Rust 改文件，Rust 通知后 JS 重新读取资源并更新界面。
- 现有 `source_storage` JSON 键值缓存属于书源引擎宿主适配，不是业务对象存储模型，也不构成引入 SQLite 或让前端管理文件的理由。

## 质量与实现约束

- 对功能意图和稳定行为做实现参考；旧版 bug、易误用流程以及只有视觉入口却未接通的功能必须先判断并正确实现，不以像素复刻为理由保留问题。
- 测试依赖按实际测试目标选择。不能因桌面 UI 构建依赖而让不需要窗口/界面的逻辑测试被迫引入同等重型系统依赖；也不为消除依赖而削弱应用运行能力。
- “完成”须有端到端功能证据：用户动作、Rust/KMP 处理、资源落盘或获取、JS 消费展示及必要的恢复/错误流程串通。单独的编译、单测或占位页面不构成功能验收。每项验证写入 [`validation.md`](validation.md)。
- 影响职责边界、持久化契约、资源 URL、跨平台能力或功能行为的取舍记入 [`decisions.md`](decisions.md)，列出依据、影响和验证状态。不得通过偏离本文件约定消解问题。
